# 2026-08-19

## Dataset refresh: a daily rotation instead of a weekly job that never finished

**What we did** — Replaced the weekly all-at-once refresh with a rolling one: each day
rebuilds the 66 least-recently-refreshed genres and lands them the same day, turning the
whole 912-genre map over in 14 days. Adds `--graph` and `--shard[=N]` modes to the
pipeline, a `refreshedAt` stamp on every detail file, bounded concurrency across the
three upstreams, and auto-merge on the daily PR. Architecture unchanged — same stages,
services and data stores; only the schedule and the unit of work changed, so no diagram
update was needed.

**The reason** — Asked what was still outstanding, the honest answer turned out to be
that the weekly refresh had **never once succeeded**, and could not. Evidence:

```
gh run list --workflow=refresh-data.yml
  2026-08-16  cancelled  5h55m   -> "exceeded the maximum execution time of 5h50m"
                                 -> reached details: 325/913 genres
gh cache list
  node-cache-...  (only entry — NO build-dataset cache at all)
```

A cold build is ~14,010 MusicBrainz requests; at the 1 req/s we are bound to, that is
4.3 h of waiting before anything else. Worse, the pipeline awaited Deezer's 6-30 s
over-quota backoffs in series with MusicBrainz, so each queue idled while the other
worked — turning a 4.3 h floor into ~12 h of wall clock.

The cancellation is what made it unrecoverable. `refresh-data.yml` asserted in its own
header that the cache "is saved to the Actions cache even when the job fails or times
out, so a rerun continues where the last one stopped". That is false for a **cancelled**
job — the `actions/cache` post-step is killed too — and `gh cache list` proves it: no
`build-dataset-*` entry ever existed. So every Sunday started cold, got a third of the
way, saved nothing, and repeated. The documented remedy (a manual re-dispatch) could not
break the loop either, because there was never anything to resume from.

**How it was solved** — Two independent changes, because either alone leaves a hole.

1. _The unit of work is a day, not a dataset._ `selectShard` takes the N oldest genres
   by `refreshedAt`. The queue is DERIVED, not stored — no cursor to drift: a new genre
   has no file so it sorts first, a deleted genre leaves by vanishing, a failed day
   corrupts nothing because those genres are still oldest tomorrow, and a corrupt file
   fails validation and so rebuilds itself. Stages 1-3 cannot shard (they decide which
   genres exist, so a sliced run would gain and lose nodes mid-rotation) and run weekly.
2. _The upstreams overlap._ `mapWithConcurrency` runs 4 genres at once and the artist
   (MusicBrainz) and track (Deezer) groups are issued together rather than in sequence.
   This is not a rate-limit change: the per-host queues in `http.ts` already space each
   host's requests regardless of how many callers are in flight, so MusicBrainz stays at
   exactly 1 req/s. What it removes is the idling.

Landing daily rather than accumulating on a branch was the owner's call, and the right
one: a branch holding a fortnight of work means the live site serves stale data for that
fortnight. Because every run leaves `public/data` complete and valid, only the AGE of a
genre varies, never whether it exists. The daily PR therefore auto-merges once `verify`
is green — a day spent waiting for review is a day the rotation stalls — which is the one
place data reaches `main` unread; `.claude/CLAUDE.md` now says so explicitly.

Two setup traps found and handled. `secrets` is not a valid context in a step-level
`if:`, so the token guard reads a job-level `env` instead. And a PR opened with the
default `GITHUB_TOKEN` does not trigger other workflows, so the required `verify` check
would never have run, the PR would have been permanently unmergeable, and the rotation
would have stalled on day one — latent in the old workflow too, hidden behind the
timeout. The workflow now fails loudly unless `REFRESH_PAT` is set. `allow_auto_merge`
was false on the repo and has been enabled.

Verified locally against the real dataset: `--shard=3` rewrote exactly 3 detail files
with `refreshedAt` stamped, and a second run picked three DIFFERENT genres — the rotation
advances. A unit test pins the fortnight, and caught that 65 genres/day is a 15-day
rotation, not 14; the constant is 66.

## Post-merge chores: exempt the automated data refresh

**What we did** — Recorded in `.claude/CLAUDE.md` (and cross-referenced from
`docs/runbooks/dataset-refresh.md`) that PRs from `refresh-data.yml` need neither the
knowledge-graph refresh nor an architecture-diagram update. Docs-only; no diagram
update needed for this change either.

**The reason** — The first automated data PR (#48) merged itself today, which put the
repo in immediate tension with its own rule: every merge is supposed to be followed by
`graphify update .`, but these merges happen unattended at 04:00 with no session to do
it in. Left as written, the rule would have been permanently violated by design — and a
rule that is always broken stops being read as a rule.

**How it was solved** — Exempted on the evidence rather than for convenience. `graphify`
extracts code structure, and `public/data/**` contributes none: the 2026-08-19 graph
rebuild listed all 915 of those files under its "produced zero nodes and are absent from
the graph" warning, so a data refresh provably cannot move the graph. Nor can it change
the architecture — same pipeline, same schedule, same output. The exemption is scoped to
the daily rotation: a hand-made change to `public/data/`, or any change to the pipeline
that produces it, is a normal merge and follows the rule.

## Mobile: the map is the screen again

**What we did** — Rebuilt the mobile layout. The controls became a top banner with two
swipeable slides (Filter · Your music) summoned by one button; the detail sheet became a
swipeable deck of topics (Songs · Deeper · Artists · Small); and the camera learned that
chrome floats over it. Desktop is untouched — it keeps the sidebar and the four stacked
lists. No architecture change, so no diagram update.

**The reason** — Phone screenshots showed the app opening to chrome with the graph
invisible behind it: both control panels mounted at once over the top and a 45vh detail
sheet over the bottom, leaving a sliver of map. Collapsed, the panels still left a large
empty rounded box. And a focused genre was centred at `height / 2` — the middle of the
CANVAS, not the middle of what you can see — so the node you just tapped sat half-hidden
behind the sheet.

**How it was solved** — The map is now the default state and controls are summoned:
nothing covers it on open beyond a 2.6rem button and a one-line "No genre selected".
Insets (`src/graph/insets.ts`, pure and unit-tested) tell the camera how much chrome
covers it, so focusing aims at the centre of the VISIBLE strip; opening the banner
re-frames by the ratio of visible heights, keeping the same content on screen smaller.
Both decks share one gesture rule (`src/mobile/slides.ts`) with a 48px threshold, so
tapping a play button inside a slide never skips it.

Three bugs surfaced only by measuring rather than eyeballing, each hidden behind the
next. Committing `lastFocusRef`/`insetsRef` ABOVE the d3-behaviour guard let the first
early-returning run swallow the change, so a deep-linked genre never zoomed. Then the
inset change interrupted the focus transition and d3 fired `end` with the half-finished
scale, which the code adopted as the intended zoom — fixed by trusting `end` only when
`sourceEvent` is non-null, i.e. a real gesture. Verified at iPhone 13 size: the focused
node lands 0px from the visible centre at zoom 4.00.

## Mobile sheet: drag to collapse, and stop sliding sideways

**What we did** — Replaced the bottom sheet's horizontal swipe deck with plain tabs,
gave it a drag handle (down to collapse, up to expand), and cut its padding. Follow-up
to the mobile layout work above, from testing on a real phone. Rendering only — no
architecture change.

**The reason** — On device the horizontal deck read as broken rather than as a gesture:
mid-swipe the heading, tab row and track list all translated together, so "DEEPER CUTS"
showed as "PER CUTS" and "Spotify" as "fy". Horizontal motion is simply the wrong axis
for a surface anchored to the bottom edge — and the tabs already switched content
without moving anything, so the sliding earned nothing. The desktop padding
(`1rem 1.25rem`) also cost a full track row of a 46vh sheet before the first song.

**How it was solved** — Tabs now swap content in place. The sheet moves on the axis it
is anchored to: a grab strip at its top takes a vertical drag (`src/mobile/sheet.ts`,
pure and unit-tested) with a 56px threshold — deliberately larger than the banner deck's
48px, because this gesture starts where a thumb rests while reading. Collapsing is
driven by `max-height`, so the existing ResizeObserver reports it and the camera
re-frames: the map grows into the space and re-centres the focused node.

One bug worth recording: the touch handler read `dragStart.current` INSIDE the state
updater. React may invoke an updater more than once (StrictMode does in development),
and by the second call the gesture had already cleared the ref — it threw and unmounted
the sheet. Deltas are captured before the updater now. Verified at iPhone 13 size: 305px
expanded, 67px collapsed, back to 305px on drag up, no console errors.

## Mobile banner: close button inline, and only as tall as its content

**What we did** — Moved the banner's close control onto the same row as the Filter /
Your music tabs, cut the header padding, and made the slide viewport size itself to the
ACTIVE slide. 239px → 194px on the Filter slide. Rendering only.

**The reason** — Three separate things were spending vertical space on a screen with
none to spare. The toggle floated in its own corner, so the banner carried `3.6rem` of
top padding purely to clear it, and the tab row underneath looked orphaned. And the
slide track is a flex row, so every slide was as tall as the TALLEST — the Filter slide
sat above a band of dead space sized by the taller ListenBrainz form.

**How it was solved** — The floating button now renders only while the banner is CLOSED;
open, the × sits at the end of the tab row (`SwipeDeck` gained a `trailing` slot), so the
3.6rem band comes back to the map. The viewport measures the active slide and sets its
own height, with a ResizeObserver because slide content changes on its own — searching
filters the list, linking an account replaces the form with genres.

The measurement alone did nothing at first: `.deck-viewport` had `flex: 1`, so it grew to
fill the deck and overrode the height that had just been measured. Its computed height
stayed at exactly 26vh while the inline style read 128px, which is what made the cause
obvious. `flex: 0 0 auto` lets the measured value win. The viewport now tracks each
slide: 194px on Filter, 305px on Your music.

## Mobile: banner open now really does collapse the sheet, and the empty band is gone

**What we did** — Two fixes from a phone screenshot: opening the top banner collapses
the bottom sheet again, and the "Your music" slide no longer sits above a band of empty
space with its last row clipped. Rendering only.

**The reason** — Both were self-inflicted.

The sheet had stopped collapsing because the rule that did it,
`.app--mobile:has(.top-banner) .detail .deck`, hid an element that no longer exists: the
sheet's internals were renamed to `.sheet-tabs` / `.sheet-list` when its swipe deck was
replaced with plain tabs. The selector silently stopped matching, and the `max-height:
none` beside it then let the sheet grow to full height — the opposite of the intent. A
parallel CSS path duplicating a state that the app already models is exactly the kind of
thing that drifts, so it is gone: `App` now applies the SAME `detail--collapsed` class
for `bannerOpen` that a manual drag applies.

The empty band was an arithmetic mismatch introduced by the height measurement. The
viewport was sized to the active slide's full `scrollHeight` (~400px) while the slide
carried its own `max-height: 26vh` (~172px), so the difference rendered as dead space —
and the list was clipped mid-row at the same time.

**How it was solved** — The cap moved off the slide and onto the measurement
(`Math.min(scrollHeight, innerHeight * 0.34)`), so viewport and content agree. That
alone left the slide overflowing, because `max-height: 100%` resolves against the flex
TRACK, whose height was its own content; giving the track `height: 100%` makes the
percentage resolve against the viewport instead. Measured after: viewport 226px, slide
226px, gap 0. Sheet 305px → 67px when the banner opens.

## Post-merge chores for PR #50, and why nothing caught the CSS regression

**What we did** — Refreshed `graphify-out/` (731 nodes, 1,572 edges, 37 communities),
updated the architecture diagram, and added the integration tests that would have caught
the banner/sheet regression.

**The reason** — Unlike the data refreshes, #50 genuinely changed the browser
architecture: two new components (`TopBanner`, `SwipeDeck`) and a new module that the
camera depends on (`graph/insets.ts`). The diagram listed only the original four
components, so it no longer described what runs.

The more interesting question was why the regression — a CSS rule targeting `.deck`
inside the sheet after the sheet stopped using that class — was invisible to everything.
Checked rather than assumed: `styles.css` contributes **zero nodes** to
`graphify-out/graph.json`, and no class name (`sheet-tabs`, `detail--collapsed`, `.deck`)
appears anywhere in it, while `GraphCanvas` and `SwipeDeck` are both present. graphify
extracts code structure by AST; a stylesheet is not in its input at all. Even if it were,
the coupling is a selector in one language matching a `className` string literal in
another — not an import, call or type, so it is not the kind of edge the graph models.
`tsc` cannot see it either, for the same reason.

**How it was solved** — The durable fix was already made when the bug was fixed: stop
expressing the state twice. `App` applies one `detail--collapsed` class for both the
banner and a manual drag, so there is no second path to drift. `tests/mobile/layout.test.tsx`
now asserts the chrome states through the rendered DOM. Verified the guard actually
guards: reintroducing the old `isMobile && sheetCollapsed` condition fails the test named
"THE regression" and passes again once restored — a regression test that does not fail on
the bug is decoration.

Diagram verified by headless render before committing, per the rule: the App.tsx box grew
from 120px to 145px to hold two more component lines, with the deep-link caption still
inside it and no overlap with the neighbouring boxes.
