# 2026-08-19

## Dataset refresh: a daily rotation instead of a weekly job that never finished

**What we did** — Replaced the weekly all-at-once refresh with a rolling one: each day
rebuilds the 66 least-recently-refreshed genres and lands them the same day, turning the
whole 912-genre map over in 14 days. Adds `--graph` and `--shard[=N]` modes to the
pipeline, a `refreshedAt` stamp on every detail file, bounded concurrency across the
three upstreams, and auto-merge on the daily PR. Architecture unchanged — same stages,
services and data stores; only the schedule and the unit of work changed, so no diagram
update was needed.

**The reason** — Asked what was still outstanding, the honest answer turned out to be
that the weekly refresh had **never once succeeded**, and could not. Evidence:

```
gh run list --workflow=refresh-data.yml
  2026-08-16  cancelled  5h55m   -> "exceeded the maximum execution time of 5h50m"
                                 -> reached details: 325/913 genres
gh cache list
  node-cache-...  (only entry — NO build-dataset cache at all)
```

A cold build is ~14,010 MusicBrainz requests; at the 1 req/s we are bound to, that is
4.3 h of waiting before anything else. Worse, the pipeline awaited Deezer's 6-30 s
over-quota backoffs in series with MusicBrainz, so each queue idled while the other
worked — turning a 4.3 h floor into ~12 h of wall clock.

The cancellation is what made it unrecoverable. `refresh-data.yml` asserted in its own
header that the cache "is saved to the Actions cache even when the job fails or times
out, so a rerun continues where the last one stopped". That is false for a **cancelled**
job — the `actions/cache` post-step is killed too — and `gh cache list` proves it: no
`build-dataset-*` entry ever existed. So every Sunday started cold, got a third of the
way, saved nothing, and repeated. The documented remedy (a manual re-dispatch) could not
break the loop either, because there was never anything to resume from.

**How it was solved** — Two independent changes, because either alone leaves a hole.

1. _The unit of work is a day, not a dataset._ `selectShard` takes the N oldest genres
   by `refreshedAt`. The queue is DERIVED, not stored — no cursor to drift: a new genre
   has no file so it sorts first, a deleted genre leaves by vanishing, a failed day
   corrupts nothing because those genres are still oldest tomorrow, and a corrupt file
   fails validation and so rebuilds itself. Stages 1-3 cannot shard (they decide which
   genres exist, so a sliced run would gain and lose nodes mid-rotation) and run weekly.
2. _The upstreams overlap._ `mapWithConcurrency` runs 4 genres at once and the artist
   (MusicBrainz) and track (Deezer) groups are issued together rather than in sequence.
   This is not a rate-limit change: the per-host queues in `http.ts` already space each
   host's requests regardless of how many callers are in flight, so MusicBrainz stays at
   exactly 1 req/s. What it removes is the idling.

Landing daily rather than accumulating on a branch was the owner's call, and the right
one: a branch holding a fortnight of work means the live site serves stale data for that
fortnight. Because every run leaves `public/data` complete and valid, only the AGE of a
genre varies, never whether it exists. The daily PR therefore auto-merges once `verify`
is green — a day spent waiting for review is a day the rotation stalls — which is the one
place data reaches `main` unread; `.claude/CLAUDE.md` now says so explicitly.

Two setup traps found and handled. `secrets` is not a valid context in a step-level
`if:`, so the token guard reads a job-level `env` instead. And a PR opened with the
default `GITHUB_TOKEN` does not trigger other workflows, so the required `verify` check
would never have run, the PR would have been permanently unmergeable, and the rotation
would have stalled on day one — latent in the old workflow too, hidden behind the
timeout. The workflow now fails loudly unless `REFRESH_PAT` is set. `allow_auto_merge`
was false on the repo and has been enabled.

Verified locally against the real dataset: `--shard=3` rewrote exactly 3 detail files
with `refreshedAt` stamped, and a second run picked three DIFFERENT genres — the rotation
advances. A unit test pins the fortnight, and caught that 65 genres/day is a 15-day
rotation, not 14; the constant is 66.
