## Fix: PR #4 merged red — prettier failure masked by a piped exit code

**What we did.** PR #4's `verify` check failed on CI, but the merge went through
anyway; this PR reformats `docs/architecture/architecture-diagram.html` with
Prettier so `main` is green again, verified locally and by re-screenshotting the
diagram (render unchanged).

**The reason.** Two failures stacked. The diagram HTML was committed without
running Prettier over `docs/`, so `format:check` failed CI. Then the merge command
chained `gh pr checks 4 --watch | tail -2 && gh pr merge` — piping to `tail` made
the chain's exit status `tail`'s success, not the check result, and because `main`
has no server-side protection (the known gap from 2026-08-04: branch protection is
a paid feature on private repos), nothing on GitHub's side blocked the red merge.

**How it was solved.** `prettier --write` on the diagram, full `npm run verify`
locally before pushing, and check status is now read from `gh pr checks`' own exit
code rather than a pipeline tail. The structural fix remains the one already in
`docs/future.md`: make the repo public or upgrade so red CI can actually block a
merge.

## Milestone 3: the map renders

**What we did.** Built the Canvas renderer and camera: `GraphCanvas.tsx` (one
imperative canvas React never re-renders), pure `camera.ts` world→screen math with
unit tests, `d3-zoom` wheel/drag/pinch plus zoom buttons, LOD-gated nodes and labels,
per-node radial gradients, structural edges in the child's dimmed colour. Zoom
round-trips through the deep-link URL.

**The reason.** Milestone 3 in `plan.md`: with the real dataset merged (#3) the pure
rules finally had something worth painting. All decision logic stayed in the tested
modules; the canvas only applies them — per the project's testing rule.

**How it was solved.** Camera = static fit transform (whole map at zoom 1 on any
screen size, so shared `?zoom=` URLs mean the same thing everywhere) composed with
the live d3-zoom transform; node radius grows with sqrt(zoom) so roots don't swallow
the screen. d3-zoom owns the transform during gestures and mirrors into React state
on gesture end only, keeping pan at canvas speed. The React-hooks compiler rule
rejected the ref-mirror pattern ("cannot access refs during render"); fixed by
closing the draw function over props and republishing it to a ref in an every-render
effect. Verified by driving headless Chromium: 9 roots at zoom 1 → 523 at zoom 8 →
912 deep in; pan and URL sync work; zero console errors. Found live: rock and
electronic hash to near-identical hues — recorded in `docs/future.md`.

## Milestone 4: focus and the panel — the core loop works end to end

**What we did.** Click-to-focus with the radial child fan on the canvas, the detail
panel reading per-genre JSON, and pipeline stages 4–5 producing that JSON for all
912 genres: `public/data/genres/<id>.json` with 5+5 songs and 5+5 artists each,
ranked by ListenBrainz listens, with streaming links from MusicBrainz URL
relationships. Zero of 912 panels came back empty.

**The reason.** Milestone 4 in `plan.md` — the product's core promise is "click a
genre, hear what lives there", and that needs both halves: the interaction (focus,
fan, camera fly-to) and the data behind it.

**How it was solved.** Fan is a pure module (`fan.ts`) returning position overrides —
the baked layout never changes, per the spatial-memory rule. Focus includes
associative children so fusion genres surface under every parent. Entities come from
tag search over-fetched to 50 (many candidates have NULL ListenBrainz data — verified
live), ranked via the bulk POST endpoints, with an obscure floor of 100 listens so
data artifacts aren't sold as hidden gems. Link kinds map from hostnames because
MusicBrainz types Spotify and Deezer identically ("free streaming"). Track links
deferred to milestone 6 with Deezer.

The ~8-hour fetch survived three incidents, each now hardened against in `http.ts`:
a kill mid-run (resumed from disk cache — the cache IS the resume mechanism), a 200
response with an empty body at genre 708 (now retried like a 503, and empty cache
entries read as absent), and a Windows EPERM on the atomic cache rename at genre 784
(antivirus briefly locks new files; now retried with a direct-write fallback).

Found and recorded in `docs/future.md`: popular-artist lists skew to megastars
because ranking is by total artist listens, not genre-scoped listens.

## Milestone 7: the weekly refresh workflow — v1 code-complete

**What we did.** Enabled `refresh-data.yml`: Sundays 04:00 UTC, rebuild the dataset,
open a PR. Wrote `docs/runbooks/hosting-cloudflare-pages.md` for the one remaining
manual step (owner connects the repo in the Cloudflare dashboard).

**The reason.** Milestone 7 in `plan.md`. The scaffold's workflow assumed a ~40-min
scrape; the real pipeline is ~9 h cold — over the 6-hour Actions job limit.

**How it was solved.** Two mechanisms make the schedule viable. The pipeline's disk
cache is stored in the Actions cache with a per-run key and prefix restore, so it
persists across runs INCLUDING failures — a timed-out first run resumes on the next
dispatch, same as locally. And scheduled runs prune only the volatile cache
directories (hierarchy pages, counts, candidate searches, rankings — the things a
refresh exists to refresh) while keeping the ~10k stable id mappings (artist
streaming links, Deezer track ids), which cuts a steady-state weekly run to
~6,000 requests ≈ 2.5–3 h. Manual dispatches skip the prune so they resume rather
than restart. The sharp-drop guard remains the gate against a silently emptied
scrape, and the PR body carries the reviewer checklist.

With this merged, every line of v1 scope in `plan.md` is built. Shipping is one
manual step: the Cloudflare Pages connection (runbook above).

## UI overhaul: from random dots to a navigable constellation

**What we did.** Owner reviewed the v1 map against its purpose ("easily find new
genres to explore") and rejected all three views: the overview read as random
specks, zoomed nodes overlapped, and the focus ring was buried in unrelated nodes
and crossing edges. Rebuilt the presentation layer around those three complaints.

**The reason.** The plain force layout scattered unrelated genres uniformly (no
visual grouping); drawn radii grew with sqrt(zoom) past the collision spacing baked
at zoom 1; and focus mode still rendered every unrelated node and edge at full
strength.

**How it was solved.**

- **Layout**: family anchors on a golden-angle ring (same rank order as the hue
  wheel, so neighbouring clusters differ in colour), singletons pushed to an outer
  halo, collision radii at 2.2x to reserve room for on-screen growth. Families now
  read as coloured constellations; the tail is a rim, not noise in the middle.
  This also closes the singleton-placement question from docs/future.md — the halo
  is the decision.
- **Overview**: LOD cutoff lowered to 10^4.3 (~48 landmarks at zoom 1), family
  roots always labelled while visible, and every sub-cutoff genre renders as a
  faint 2px dust mote so the map keeps its galaxy shape at all zooms.
- **Overlap**: radius growth cut to zoom^0.35, and a new pure `labels.ts` greedily
  places labels by priority, dropping any that would overlap a more important one.
- **Focus**: unrelated nodes dim to 12% with no labels, unrelated edges vanish
  (spokes only), and bystanders inside the fan ring are displaced just outside it
  (`ringClearance` in fan.ts — a rendering transform, baked layout untouched, per
  the owner's explicit OK to move things while zoomed).
- **Feel**: hover ring + label + pointer cursor; node gradients gained a soft rim.

Verified in headless Chromium against the owner's three screenshots: overview shows
48 labelled landmarks in colour territories over dust; the country cluster at zoom 6
has zero overlaps and clean labels; the house ring is evenly spaced, fully labelled,
with everything else receding. 156 tests green.
