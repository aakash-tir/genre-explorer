## ListenBrainz fallback: count raw listens when the stats pipeline has nothing

**What we did** — Added a fallback to the personal lens's public intake
(`src/personal/listenbrainz.ts`): when every stats range returns 204, the app pages
the raw listens feed (`/1/user/{name}/listens`, up to 3 × 1000 newest listens) and
ranks artists by play count client-side. New pure function `topArtistsFromListens`
plus `fetchRecentListens`, both unit-tested; the stats-pending error now only fires
for accounts with no listens at all, with wording that no longer promises "tomorrow".

**The reason** — A real account (`aakash-tir`, 74,489 listens imported from Spotify)
showed stats on listenbrainz.org's dashboard but got "no stats yet" in the app.
Live probing showed every stats range (`week` … `all_time`) returning 204, while a
long-established account's stats carried `last_updated` 2026-07-05 — ListenBrainz's
stats batch pipeline had not run in over five weeks, so any account whose listens
arrived after that has no computed stats at all. The research doc's "within a day"
assumption (§3 caveats) was too optimistic; doc updated.

**How it was solved** — Listens carry `mbid_mapping.artists[].artist_mbid`, the
dataset's own primary key, so the fallback keeps exact matching for everything
ListenBrainz has mapped. Tallies are keyed by normalized artist name (mapped and
unmapped listens of one artist merge); an mbid or Spotify id is kept only when all
of an artist's listens agree on it, so name collisions degrade to name matching
instead of crediting the wrong artist. Verified end-to-end in the running app:
the lens renders genres for `aakash-tir` from 3,000 recent listens. Architecture
unchanged (same external service, same scoped network exception) — no diagram
update needed.

## Song rows link out to Spotify and Deezer

**What we did** — Added `src/lib/trackLinks.ts` (pure, unit-tested) and wired it
into `DetailPanel`'s track rows, so every song now shows a Spotify link and, when
stage 6 resolved a preview id, an exact Deezer link — rendered in the same place
the artist rows already put theirs, right after the listen count.

**The reason** — Song rows had a `<Links>` element from the start, but
`Track.links` is emitted empty (deferred out of milestone 4), so it always
rendered nothing. Songs were the one thing on the panel you could not click
through to.

**How it was solved** — The Spotify link is a SEARCH deep link, not the track's
own page, and that is a forced choice rather than a shortcut. Two exact-link
routes were probed live before settling: MusicBrainz
`recording/{mbid}?inc=url-rels` returned **zero** URL relations for four real
dataset tracks (artist-level coverage is ~68%, recording-level is ~0, so a
per-recording pass would add ~9,000 requests at 1 req/s to buy almost nothing);
and Odesli/song.link — the obvious free Deezer→Spotify bridge — resolves a Deezer
track to Amazon, Tidal, Napster, Anghami, Boomplay and Yandex while omitting
Spotify entirely, confirmed against Daft Punk's "Get Lucky" and cross-checked by
feeding it a Spotify URL (it echoes Spotify back, so it only ever passes the
input through). An exact per-song Spotify URL therefore needs the authenticated
Spotify API, which the no-keys rule forbids — recorded in `docs/future.md`.
Deezer, by contrast, is exact for free: the id is already in the dataset.
Derived links yield to any real dataset link, so a future pipeline that bakes
track links takes over silently. Verified in the running app via a headless DOM
dump — Unicode titles encode correctly (`MACABRE－揚羽ノ羽ノ夢ハ蛹－`), and both
generated URL shapes return 200. Architecture unchanged (no new service, no new
runtime call — the links are plain anchors) — no diagram update needed.

## Removed Spotify owner mode from the personal lens

**What we did** — Deleted the personal lens's Spotify OAuth intake ("owner mode"):
`src/personal/spotifyAuth.ts`, `spotifyClient.ts`, their test, the owner-mode
disclosure in `PersonalPanel.tsx`, token state in `storage.ts`, the OAuth callback
handling in `usePersonal.ts`, the `VITE_SPOTIFY_CLIENT_ID` bake in
`deploy-pages.yml`, and the runbook `docs/runbooks/spotify-personal-mode.md`.
The ListenBrainz username path is now the lens's only intake.

**The reason** — The owner decided not to use it and never registered the Spotify
app, so the code path was unreachable by anyone: no client id existed, and dev-mode
policy capped it at 5 allowlisted users even if one had.

**How it was solved** — Pure removal, no behaviour change on the surviving path.
The matching layer keeps its Spotify-id key (`match.ts`, `ArtistIndexEntry.spotifyId`)
because the ListenBrainz intake also supplies Spotify ids from listen metadata, and
the dataset's outbound Spotify links are unrelated (they come from MusicBrainz).
Stored `v2` localStorage values from the old mode fail the Zod parse and degrade to
"not connected" as designed. Architecture changed (an external service and its flows
dropped) — diagram update due in the post-merge chores.
