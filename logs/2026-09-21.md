# 2026-09-21

## Rolling refresh: a failed genre now fails only itself

**What we did** — The daily shard keeps the genres that succeeded instead of discarding
them. A genre whose upstream calls fail is skipped and logged by id; the rest are
written and land in the day's PR as usual. Two ceilings bound the tolerance: a run still
exits non-zero if more than 25% of the shard failed (or more than 2 genres on a small
manual shard), and the build step is killed at 90 minutes with the workflow arranged to
survive that kill. Pipeline and workflow only — no architecture change, so no diagram
update was needed.

**The reason** — Asked for the state of the project, the interesting number was in
`gh run list`: since the rolling rotation launched on 2026-08-19, **12 of ~34 scheduled
runs failed or were cancelled**. Every diagnosed one was a single transient upstream
error, spent after five retries:

```
2026-09-10  failure   MusicBrainz recording?query=tag:"trova"          503
2026-09-12  failure   MusicBrainz artist?query=tag:"tropical house"    503
2026-09-16  failure   ListenBrainz /1/popularity/artist   connect ETIMEDOUT
2026-09-20  cancelled 2h0m20s — hit the job ceiling (NOT diagnosed)
```

`mapWithConcurrency` rejects on the first failure, so `buildDetails` threw, the step
exited non-zero, and the commit/PR steps never ran — throwing away the ~65 genres that
had already been fetched, ranked, linked and written to disk. One genre in 66 was
discarding the other 65. The cost was visible in the data: `refreshedAt` across the 912
detail files spanned 2026-08-31 to 2026-09-21, so the real rotation was ~21 days against
a designed 14.

Worth being precise about what was NOT broken. The rotation itself works — PRs #52–#70
opened, passed `verify` and auto-merged unattended, every genre had been refreshed, and
no day ever corrupted anything. This was purely a case of correct work being thrown away
at the last moment.

**How it was solved** — The retry mechanism is the queue that already exists. A failed
genre is simply not written, so its old `refreshedAt` survives, so `selectShard` puts it
at the head of tomorrow's shard. Nothing records the failure, because a derived queue
cannot drift out of step with what was actually written (`rotation.ts` says this about
failed DAYS; it turns out to be just as true of failed genres). `buildDetails` catches
per genre rather than loosening `mapWithConcurrency`, whose abort-on-first-rejection is
still right for the graph stages, where a partial result would mean the map gaining and
losing nodes.

The ceiling exists because the opposite failure looks identical from inside a single
genre: if the upstream is down rather than flaky, a run that "tolerated" 60 failures has
refreshed nothing and a PR for it every morning would teach us to ignore the PR.
`judgeShard` is pure and unit-tested.

Two things the tests caught that the design had wrong:

- A percentage-only ceiling reverts to all-or-nothing on a SMALL shard — at
  `--shard=4`, one flaky genre is 25% and would abort the run, which is the exact
  behaviour being removed, just at the size that bites a manual repair dispatch. Hence
  `MIN_TOLERATED_FAILURES = 2`: whichever rule is kinder wins.
- Stage 9 (the artist index) is the last thing `buildDetails` does, so a killed step
  never reaches it and would commit panels with an index describing the older ones. It
  is a pure re-read of our own output with no network, so the workflow now reruns it
  unconditionally after the build step.

The 90-minute kill needed workflow-level handling, because a SIGKILLed process cannot
catch anything: the build step is `continue-on-error` with a step ceiling below the job
ceiling, the index is reconciled, `npm test` still gates the PR on the partial data
being schema-valid and internally consistent, and a final step marks the run red. The
data lands and the bad day is still visible — previously it was one or the other.

Verified the regression tests actually fail on the bug, per the project's rule:
reinstating the rethrow in `buildDetails` fails four of the five tests in
`tests/scripts/build-details.test.ts`, and they pass again once removed. Full `verify`
green at 309 tests (was 295).

## The Sunday graph rebuild has never once succeeded

**What we did** — Moved the refresh's time budget off the job and onto the steps: the
graph rebuild gets 240 minutes, the details shard keeps 90, and the job ceiling rises
from 120 to 350 as a pure runaway guard. Corrected the two stage estimates in
`index.ts`, which were roughly half of what the stages actually cost. Workflow and
comments only — no architecture change, so no diagram update.

**The reason** — Asked to diagnose the 2026-09-20 two-hour cancellation, the pattern
turned out not to be about that run at all. Splitting every scheduled run by weekday:

```
--- SUNDAY (graph + details) ---        --- MON-SAT (details only) ---
2026-09-20  cancelled  120.3m           20 of 29 succeeded
2026-09-13  cancelled  120.3m
2026-09-06  cancelled  120.3m
2026-08-30  failure     74.4m
2026-08-23  cancelled  120.3m
2026-08-16  cancelled  355.3m
2026-08-09  failure     33.0m
```

Seven Sundays, seven failures, no successes. Sunday is the only day that runs `--graph`,
so stages 1-3 have never completed under the automation at all: `graph.json` still read
`builtAt: 2026-08-18`, written by hand in PR #45. For 34 days no genre entered or left
the map and no node changed size, however much MusicBrainz moved underneath it.

The run dies in `Rebuild graph`; every later step is skipped, so Sunday contributed
nothing to the details rotation either — a seventh of the rotation lost on top of the
frozen map. Timings from the 09-20 log:

```
09:09:02  stage 1: genre list      2202 genres (30 s)
09:09:32  stage 2: hierarchy       claimed ≈ 40 min
10:18:27    ...took 69 min         2202 pages at ~1.88 s each, not the bare 1.1 s
10:18:27  stage 3: popularity      same request count, so ~70 min needed
11:09:01  KILLED at the 120-minute job ceiling, ~50 min into a ~70-minute stage
```

The graph needs ~140 minutes; the whole job had 120, before the details shard ran. It
could not have succeeded on any Sunday.

What made it unrecoverable rather than merely slow is the same trap this project
documented on 2026-08-19 and fixed only on the details path. A JOB timeout CANCELS the
job, and a cancelled job skips its post-steps — including the `actions/cache` save. So
each Sunday pruned the graph caches by design, scraped for two hours, saved nothing, and
started next Sunday from exactly the same place. `gh cache list` is the proof: every
surviving entry is a weekday run id, not one Sunday among them.

**How it was solved** — A STEP timeout only FAILS the step, so the later steps and the
post-steps still run and the cache is kept. The budget therefore belongs on the steps,
and the job ceiling should be nothing but a runaway guard — at 120 it was instead the
thing killing every Sunday, in the one way that preserves no progress. The graph step
gets 240 minutes (~1.7× the measured need) and `continue-on-error`, so an overrun now
fails loudly, keeps its cache for next week, and no longer skips the day's details
shard. 350 for the job sits just under GitHub's 360-minute hard limit.

The stale estimates were part of the cause, not a cosmetic detail: "cold cache ≈ 40 min"
against a real 69 is what made a 120-minute ceiling look generous when it was never
survivable. Both now say ~70, with the measurement recorded beside them.

One asymmetry worth stating plainly, because it is now the sharpest edge in the
schedule: a failed GENRE self-heals, because the queue is derived from `refreshedAt` and
puts it back at the head tomorrow. A failed GRAPH does not — stages 1-3 run only on
Sundays, so a bad week costs a week unless someone dispatches `mode=graph` by hand. The
runbook and `docs/future.md` both say so.
