# 2026-08-17

## Favicon: give the app a real icon instead of a 404

**What we did** — Added `public/favicon.svg` and linked it from `index.html`.
Cosmetic only — no source, dataset or architecture change, so no diagram update
was needed.

**The reason** — Driving the running app in a headless browser surfaced a console
error on every page load: `GET /favicon.ico 404`. There was no icon file anywhere;
`index.html` declared no `<link rel="icon">`, so the browser fell back to the
default `/favicon.ico` path and missed. Worth noting for anyone probing this in
dev: curling `/favicon.svg` returned `200` _before_ the file existed, because
Vite's dev server answers unknown paths with the SPA fallback (`index.html` at
`content-type: text/html`). A status code alone doesn't prove an asset exists —
check the body.

**How it was solved** — The icon is the map in miniature: one vivid family root
with five subgenres radiating out on the app's `--bg` (`#08080c`). Colours are
derived from `src/graph/colors.ts` rather than picked by eye — satellite hues are
the first five steps of the golden-angle sequence, and each satellite sits one
step down the depth ramp from the root (saturation 78→67, lightness 52→58), so the
icon fades outward the way real nodes do. Only `subgenre of` edges are drawn, per
the edge rule. Verified at 16/32/64px: legible as a distinct cluster at tab size,
and the dark rounded plate keeps it readable on a light tab bar. Confirmed in the
browser that the load is now clean — zero failed requests, zero console errors —
and that `dist/favicon.svg` ships in the production build.

## Genre membership: gate on tag votes instead of search rank

**What we did** — Three linked changes to how an artist or song comes to belong to a
genre, plus the dataset rebuild that makes them real (860 detail files, and
`artist-index.json` rebuilt at 6,956 artists). Architecture unchanged — same stages,
same external services, same schedule — so no diagram update was needed.

**The reason** — Reported from the personal lens: Coldplay was listed under `indie
rock`. Investigating showed Coldplay carries **no `indie rock` tag on MusicBrainz at
all**, and neither `ambient`, `ambient pop` nor `indie pop` — four of their ten
indexed genres were fabricated outright. The root cause is that MusicBrainz search
relevance is not tag agreement. `tag:"indie rock"` returns:

```
score=100  The Beatles   indie rock tag: -3   <- net-negative, actively voted down
score=97   Pearl Jam     indie rock tag:  2
score=92   Nirvana       indie rock tag:  0
score=90   Radiohead     indie rock tag:  4
```

Stage 4 kept the top 50 and discarded both the relevance score and the tag counts;
stage 5 then ranked purely on total listens, so a loose match on a megastar beat every
genuine member. That is how The Beatles reached 39 genres including `heavy-metal`,
`classical` and `filk`, and how `Various Artists` — not an artist — reached 30 panels.
The backlog had already predicted the shape of the fix on 2026-08-07 ("mitigations
would be heuristic, e.g. weight by tag count"), parked in `docs/review/` as the open
decision that most changes what users see.

**How it was solved** — The vote count is now the gate, not the search rank.

1. Stage 4 admits a candidate only if it carries the genre's own tag with
   `>= MIN_TAG_VOTES` (1), and blocks seven MusicBrainz placeholder MBIDs outright.
   The counts ride along in the SAME search response, so this costs no extra requests —
   an assumption worth checking before designing around a per-entity fetch. Threshold
   chosen by measuring the whole 912-genre response cache offline: `>= 1` keeps 90.8%
   of artist candidates and empties 3 genres, where `>= 2` keeps 22.3% and empties 106.
2. Stage 5 ranks "popular" on `sqrt(votes) * log10(listens)`. Listens alone had left
   britpop headed by The Beatles on ONE vote while Oasis, with 14, sat fifth. "Obscure"
   still ranks on listens alone — that is a pure listen-count question — but now draws
   from the same tag-gated pool.
3. Tag votes are carried through the detail files into `artist-index.json` (a schema
   change, so `tsc` failed on both sides at once as intended), letting the personal lens
   weight each genre by `sqrt(votes / the artist's strongest tag)` instead of crediting
   every genre in full.

Smoothing the vote term (`sqrt(votes + k)`) was tried and REJECTED, which is the
non-obvious part. About a third of panels are thin enough that every member sits at 1-2
votes, and there one extra vote outweighs an order of magnitude of listens — `boogie`
ranks Dua Lipa (2 votes, 1.7M) above Michael Jackson (1, 29M). Smoothing fixes that and
breaks a worse case: in `bolero` it promotes Gloria Estefan (1 vote, 871k listens) over
Gilberto Santa Rosa (2, 116k) and Julio Jaramillo (2, 36k), a famous outsider displacing
two canonical members. That is the original bug in miniature and it lands hardest on
non-Western genres, so the thin-tag jitter is the accepted cost. Pinned with a
regression test using the real bolero numbers.

Verified in the running app: britpop leads Blur, Oasis, Pulp and its songs are Kula
Shaker, Shed Seven, Supergrass, "Three Lions"; ambient leads Brian Eno and Tangerine
Dream; rock is unchanged at The Beatles, Queen, The Rolling Stones. Coldplay is down to
alternative-rock (34 votes) and post-britpop (3); The Beatles from 39 genres to 6, all
defensible; `Various Artists` is gone. Artists appearing in more than 10 genres fell
from 29 to 2, while the total artist count ROSE from 6,548 to 6,956 — panels now hold
genuine members instead of repeating the same megastars. One genre is left with no
entities at all, which the panel states honestly.
