## Research: personal "your genres" subgraph from listening history

**What we did.** Owner asked whether users could connect Spotify and see a subgraph
of their listened genres plus similar ones to branch into. Researched it and wrote
`docs/research/listening-history-personalization.md`; added the feature to
`docs/future.md` under Deferred from v1.

**The reason.** The naive design ("create an account and connect Spotify") collides
with both the access reality — Spotify dev mode is capped at 5 allowlisted users and
extended quota needs a 250k-MAU organization (per the 2026-08-04 research) — and the
project's no-backend/no-accounts architecture. Worth establishing what IS possible
before the idea calcified as impossible or got built the wrong way.

**How it was solved.** Verified live (2026-08-10) that ListenBrainz's stats API
serves a user's top artists with MBIDs, unauthenticated, with `Access-Control-Allow-Origin: *`
— and ListenBrainz auto-imports Spotify listens, making it the bridge. Confirmed via
the Feb 2026 changelog that Spotify's own `/me/top/*` endpoints survived (viable only
as a ≤5-user personal mode). Conclusion: feasible with no backend and no accounts —
ListenBrainz intake (MBID-exact) plus a client-side Spotify GDPR-export upload
(name-matched), a new build-time artist→genre reverse index from stage 4's existing
candidates, branch-out suggestions from the fusion/influence edges already in
`graph.json`, and `localStorage` persistence. One scoped exception to "network calls
at build time only" (api.listenbrainz.org, user-initiated). Docs-only change — no
diagram update.

## Personal lens: Spotify personal mode (≤5 users), your genres + branch-out

**What we did.** Built the feature the morning's research scoped, in its
personal-mode form per the owner's decision ("do this for the 1-5 users for now
and can expand later"). New: `public/data/artist-index.json` (artist → genre
reverse index, 6,548 artists, inverted from the committed detail files by a new
pipeline stage 9, `emit-artist-index.ts`); `src/personal/` — client-side OAuth
PKCE against the owner's dev-mode Spotify app (scope `user-top-read` only),
top-artists fetch (long+medium term merged), pure `match.ts` (spotify-id exact,
unambiguous-name fallback, rank-weighted) and `suggest.ts` (fusion/influence >
parent/child > sibling adjacency over edges already in graph.json), all
persisted in `localStorage`; a "Your music" panel under the filter; and a map
lens — matched genres ringed by weight, suggestions dash-ringed, the rest
dimmed, lens genres always visible via a new `personal` set in `lod.ts`
(filter still gates, labels unchanged).

**The reason.** Owner wants their own listening history on the map now; the
public paths (ListenBrainz bridge, export upload) stay in `docs/future.md`. The
architecture concedes exactly one scoped runtime-network exception
(accounts/api.spotify.com, user-initiated, map never depends on it) — recorded
in CLAUDE.md and project-context.

**How it was solved.** PKCE needs no secret so a static site can do the whole
flow; the callback query is captured at module load because App's URL-sync
effect would otherwise eat `?code=` in a race; StrictMode double-effects are
guarded (the code is one-shot). Matching refuses ambiguous names — a wrong
highlight is worse than a missing one. Verified end-to-end with a seeded
localStorage profile against the real index in headless Chromium (screenshots:
panel, lens rings, panel-click → camera flight → detail panel); 44 new unit
tests incl. the RFC 7636 PKCE vector. Owner setup runbook:
`docs/runbooks/spotify-personal-mode.md`; deploy workflow bakes
`SPOTIFY_CLIENT_ID` repo variable when set. Architecture changed (new runtime
external service + new data artifact) — diagram update due with the post-merge
chores.
