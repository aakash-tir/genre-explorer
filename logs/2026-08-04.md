# 2026-08-04

## Expanded the plan from a sketch into a scaffolded project

**What we did.** Took `plan.md` — a rough page describing a zoomable music genre graph —
and turned it into a researched plan, a decided tech stack, a working skeleton with a
real test suite, CI that gates merges, and a private GitHub repo with `main` protected.
No product features were built; the finish line was a repo someone can clone, run the
tests in, and know what to build first.

**The reason.** The original plan named a shape ("a graph of music genres, node size by
popularity, panel with songs and artists on the right, subgenre gradients") but was
silent on everything that decides whether it can be built: where the genre hierarchy
comes from, where the songs and artists come from, and what happens to the ~40% of genres
nobody has tagged. Those are not implementation details — they are the difference between
a viable project and a month of work ending in an empty map.

**How it was solved.** Research first, verified against live requests rather than memory.

## Research: Spotify turned out to be a dead end, and MusicBrainz turned out to be perfect

**What we did.** Checked whether the plan's assumed data source — Spotify — could supply
popular songs and artists per genre. It cannot, for a project starting now. Then found
and verified a replacement pipeline end to end.

**The reason.** The plan assumed Spotify links implied Spotify data. Two waves of
deprecation say otherwise:

- **Nov 27 2024** — apps approved after that date lost `/recommendations`,
  `/audio-features`, `/audio-analysis`, `/artists/{id}/related-artists`, and 30-second
  `preview_url`s.
- **Feb 2026** (from Spotify's own changelog) — `/artists/{id}/top-tracks` removed for
  everyone, along with all browse and batch endpoints. Search `limit` cut from 50 to 10.
  The app owner must hold Premium. Dev mode caps at five users. Extended quota has, since
  May 2025, only been granted to organisations with 250k+ monthly active users.

`/artists/{id}/top-tracks` was precisely the endpoint the right-hand panel needed. There
is no path to it at this scale, so the entire data strategy had to change before any code
was written.

Every Noise at Once — the obvious prior art — was also ruled out: frozen since Glenn
McDonald's December 2023 layoff, and more importantly it has no hierarchy at all, only
similarity coordinates. Our whole product is the tree.

**How it was solved.** MusicBrainz + ListenBrainz, verified with real HTTP calls:

- `GET /ws/2/genre/all?fmt=txt` → **2,184 genres**
- MusicBrainz models `subgenre of`, `fusion of` and `influenced by` **between genres**.
  The `alternative rock` page really does list `subgenre of: rock`, twelve subgenres, and
  `has fusion genres: alternative dance`. This maps one-to-one onto the plan's own rule
  that a fusion genre's edges exist in the data but are never drawn.
- `GET /ws/2/artist/{mbid}?inc=url-rels` returns canonical `open.spotify.com` and
  `soundcloud.com` URLs — so the plan's Spotify/SoundCloud links are satisfied by a CC0
  database without touching the Spotify API at all.
- `POST api.listenbrainz.org/1/popularity/artist` returned 14,807,187 listens for Aphex
  Twin; `/popularity/recording` returned a spread from 5,286 down to 1. That spread is
  the popular-versus-obscure split the panel needs.

Written up with the raw responses in `docs/research/music-data-sources.md`, plus
`graph-rendering.md` and `hosting.md`.

## Found the hard part: MusicBrainz hides the hierarchy from its own API

**What we did.** Established that the genre relationships — the single reason MusicBrainz
was chosen — are not retrievable from the JSON web service, and designed around it.

**The reason.** This is the failure mode worth recording, because it fails _silently_:

```
GET /ws/2/genre/{mbid}?inc=genre-rels&fmt=json  → 200 OK, "relations" absent
GET /ws/2/genre?query=alternative%20rock         → {"error": "This hasn't been implemented yet."}
```

The `inc` parameter is accepted and returns nothing. A pipeline that trusts it emits
2,184 orphan nodes, no tree, and no error. Nothing looks broken until the map renders as
dust. Probed `inc=genre-rels`, `artist-rels` and `url-rels` on the `alternative rock`
MBID — all returned `relations: 0`, while the HTML page for the same MBID lists them
plainly.

**How it was solved.** Two routes exist: the 7 GB `mbdump.tar.bz2` full export (which has
`l_genre_genre`, but needs a Postgres import in CI for a few thousand rows), or scraping
the 2,184 genre HTML pages at MusicBrainz's 1 req/s limit — roughly 37 minutes, once,
cached to disk. Chose the scrape, with three guardrails written into the design before
any code: the parser is isolated in one module with fixture tests over saved real pages;
stage 8 of the pipeline fails the build if edge counts drop sharply against the committed
dataset; and the dump import stays documented as the fallback.

Also found the second-order problem: `acholitronix` is a real MusicBrainz genre with
**zero** tagged release-groups, while `rock` has 547,091. Roughly 40% of genres cannot
fill a panel. That is the direct reason for the threshold filter in pipeline stage 3, and
the reason node radius must be log-scaled.

## Decisions taken with the user

**What we did.** Asked four questions, each with concrete consequences rather than labels.
All four recommendations were accepted.

- **Genre scale** — filtered auto-build, ~800–1,200 genres clearing a data threshold,
  over hand-curation (ages badly, manual re-curation on every refresh) or the full 2,184
  (hundreds of empty panels).
- **Layout** — force constellation with a radial focus mode on click, over a pure force
  map (dense families stay tangled) or a radial tree (reads as an org chart).
- **Renderer** — Canvas 2D with `d3-zoom`, over Sigma.js (per-node gradients would need
  custom GLSL, making the signature visual the hardest code in the repo) and
  react-force-graph (re-simulates on load, so the map moves between visits).
- **v1 extras** — all four accepted: audio previews, deep links, weekly refresh, and
  touch/mobile.

The scale decision is the one that most changes the product: it trades exhaustiveness for
the guarantee that every node opens to something real.

## Built the skeleton and the tests that make it a gate

**What we did.** React 19 + TypeScript + Vite 8 project with the three rules that define
the interaction implemented as pure, tested functions — `src/graph/edges.ts` (which edges
are drawn), `lod.ts` (what is visible at a given zoom/focus/filter), `colors.ts` (family
hue, depth gradient) — plus `src/lib/deepLink.ts` and the Zod dataset schema. 92 tests
across 6 files. `npm run verify` runs lint, format, typecheck, test and build.

**The reason.** These four rules are all easy to get subtly wrong and impossible to
verify by looking at a canvas. The fusion rule in particular — "show `alternative dance`
under both `alternative rock` and `dance`, but never draw an edge between them" — is
exactly the kind of thing that silently regresses. Keeping the decision logic pure and out
of the render loop is what makes it testable at all.

**How it was solved.** Wrote the tests against a fixture graph shaped around the real
`alternative dance` case. Five failed on the first run, which was the point — they can
fail:

- Three LOD tests: `MIN_VISIBLE_EXPONENT = 4.5` / `FULL_DETAIL_ZOOM = 32` made the cutoff
  fall too fast, so zoom 1 already revealed five of eight genres instead of the two family
  roots. Retuned to `5` / `64`, which puts the zoom-1 cutoff at 100,000 release-groups —
  correct for a dataset where `rock` is 547,091.
- One deep-link test: `URLSearchParams.toString()` percent-encodes the comma separator, so
  `?filter=techno,house` came out as `techno%2Chouse`. Since genre ids are already
  restricted to `[a-z0-9-]`, nothing needs escaping — the query string is now built by
  hand so shared links stay readable.
- One App test, which was downstream of the LOD constants.

Also hit a config issue: Vitest 4 types the `test` key through its own `defineConfig`, so
keeping it in `vite.config.ts` made `tsc` reject the Vite config. Split into
`vitest.config.ts`.

Final run: **92 passed, 6 files.** Build output 260 KB (79 KB gzipped).

## CI, and one deliberate omission

**What we did.** `.github/workflows/ci.yml` with a single `verify` job on pull requests
and pushes to `main`, npm caching, and a step summary reporting bundle and `graph.json`
sizes. PR template covering what/why/how-tested plus the post-merge artifact checklist.
`.github/workflows/refresh-data.yml` for the weekly dataset rebuild.

**The reason for the omission.** The refresh workflow's `cron` schedule is commented out.
`npm run build:dataset` is a stub until milestone 2, so an enabled schedule would fail
every Sunday and train everyone to ignore a red workflow — which is worse than having no
schedule at all. It gets uncommented in the PR that lands the pipeline.

**Note on artifacts.** This day was scaffolding, not architecture change against an
existing system — but the architecture is now defined, so
`docs/architecture/architecture-diagram.html` is genuinely absent rather than merely
unchanged. It should be authored during milestone 2, once the pipeline exists in code
rather than only in prose.
